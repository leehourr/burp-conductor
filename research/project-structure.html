Project reference · 2026-11-21

burp-conductor

An MCP plugin that wraps PortSwigger's Burp MCP extension with a safety spine, an engagement state model, and a six-phase pentest workflow. Any MCP-capable AI harness drives the engagement; Burp stays the proxy, scanner, and attack engine. Written so the operator — not the model — controls what goes out, what gets written, and where the work resumes.

1. What it is

burp-conductor is a Python stdio MCP server that sits between an AI harness and PortSwigger's official Burp MCP SSE extension. The harness talks to burp-conductor; burp-conductor talks to Burp on 127.0.0.1:9876. Every request crosses a safety layer (safety.py) before it reaches Burp, and every response is capped, sanitized, and quarantine-tagged before it reaches the model.

Alongside the proxy wrapping, the plugin adds three things the raw Burp MCP does not have:

  • Engagement state. reports/<slug>/engagement.yaml is the source of truth — scope, auth, phase status, verify queue, findings index. A fresh session rehydrates from it with /pentest-resume.
  • A six-phase workflow. recon → auth → access → inject → roundout → report. Each phase is a slash-command skill that reads engagement.yaml, enforces its prereqs, and writes back on checkpoint.
  • A free-stack replacement for Burp Pro's Crawl / Active Scanner / Collaborator — Katana, Nuclei (fast + headless + authenticated), interactsh, and an in-repo diff_fuzz.py that stands in for Backslash-Powered Scanner.
One-sentence pitch: "Burp MCP is a protocol; burp-conductor is the discipline — scope, HITL, state, and a repeatable six-phase workflow around it."

2. Why it exists

Three problems the raw PortSwigger extension does not solve, each of which would otherwise fall to the operator remembering to do the right thing on every call.

2.1 Raw Burp MCP has no safety

The official server exposes 26 tools that let a model fire HTTP, queue Intruder attacks, and read proxy history. None of them check scope, none of them gate on human approval, none of them scrub auth from logs, and none of them cap or quarantine responses that come back carrying prompt-injection payloads. A pentest harness that fires at an out-of-scope host is a billable incident; burp-conductor makes that structurally impossible.

2.2 Burp Community has no persistence

Burp Community (free edition) does not save project state. Close the window, lose the proxy history, the Repeater tabs, the Intruder attacks, the scanner issues. An engagement that runs across three days on Community would normally mean starting fresh three times. burp-conductor moves the engagement memory out of Burp and into engagement.yaml + per-finding markdown + daily JSONL logs, all on disk under reports/<slug>/. Burp becomes a stateless execution engine.

2.3 A pentest is not a chatbot turn

Recon is not injection, and injection is not reporting. Each phase has its own tools, its own HITL posture, its own prereqs. The six-phase skills give the harness a workflow to follow instead of a toolbox to flail inside — the roadmap box prints on every anchor moment so the operator (and the model) always know where they are.

4. The six-control safety spine

All six controls live in safety.py and are enforced by server.py on every tool call. They are not configurable per-call; they are structural.

#ControlWhere enforcedWhat it prevents
1Scope-incheck_in_scope() on every tool that takes a URLFiring at a host not in SCOPE_HOSTS. Rejects before upstream call.
2HITL gateHITL_PER_CALL / HITL_PER_PHASE; skills announce before firingAutonomous active traffic. Per-call for Repeater / Intruder / raw HTTP sends. Per-phase for scanner and batch replay.
3Response cap + quarantinespotlight_wrap() on every returned bodyPrompt-injection from the target bleeding into model context. Caps at 8 KB, wraps in <untrusted-tool-output>, tags quarantine="true" on hits like "ignore all previous instructions".
4Report confinementconfine_report_path() on every writePath traversal out of reports/. Any resolved path that escapes REPORTS_ROOT is rejected.
5Auth scrubbinglog_request before JSONL appendLive tokens / cookies written to disk. Strips Authorization, Cookie, Set-Cookie, X-API-Key, X-Auth-Token, Proxy-Authorization.
6Identity headerinject_identity_into_raw() on every outbound upstream callOur traffic reading as a genuine attack to the client's blue team. Injects a client-whitelisted header (default X-Pentest-ID) so SIEM / WAF rules can filter us out. Value convention <company>/<slug>/<yyyy-mm-dd>.
Identity header applies to standalone tools too. Nuclei, Katana, and diff_fuzz run via Bash, not MCP, so inject_identity_into_raw does not touch them. Phase skills must pass the same value via -H / --header. engagement.yaml is the single source of truth — if the value changes mid-engagement, change it there and reload.

HITL tiers — what each means in practice

  • Per-call HITL. Announce tool + target + payload shape. Wait for explicit "go". Every single invocation. Applies to send_http1_request, send_http2_request, create_repeater_tab, send_to_intruder.
  • Per-phase HITL. Announce once at phase start (scope, mode, rate, templates). Wait for go. Phase then runs without re-prompting unless something unusual happens. Applies to the scanner trigger (name TBD per list_upstream_tools) and local batch-replay.
  • Passive, uncounted. http_get and get_proxy_history are scope-checked but not HITL-gated; they fetch without sending new attack traffic.

      │

A session that lost its context picks up exactly where the last one stopped. No ad-hoc memory, no "where were we." The file is the memory.

6. Six phases (and what's dropped)

PTES ships seven phases; OWASP WSTG ships eleven categories. burp-conductor ships six. The reduction is deliberate — a web-app engagement does not need post-exploitation, and pre-engagement is email work, not harness work.

PhaseSkillWhat it doesHITL posture
recon/pentest-reconEndpoints, hidden params, auth boundary, threat model. Passive only — no active probes.None; no attack traffic fires.
auth/pentest-authLogin rate-limit, user enumeration, session fixation, JWT weakness, reset/MFA flow.Per-call on every send / repeater / intruder.
access/pentest-accessIDOR (object-level), vertical priv-esc (function-level), business-logic abuse.Per-call. One object at a time, no mass sweeps.
inject/pentest-injectSQLi, XSS, SSRF, method/content-type tampering. Drives scanner pass on verify_queue.Per-phase on scanner. Per-call on every manual payload. interactsh canary before any SSRF.
roundout/pentest-roundoutOWASP Top-10 sweep — headers, TLS, SCA, crypto, design, integrity, logging, races. Safety net for everything the earlier phases missed.Passive reads free. Active probes gated per-call.
report/pentest-reportAssemble EN draft from per-finding markdown, hand off to Otoi-san for JP translation, prepare debrief.No upstream fires. Read, assemble, write only.

What we dropped and why

Pre-engagement / scopingFolded into /pentest-start + SCOPE.mdReal work but not harness work — email + signed SOW. The technical phases consume its outputs (scope hosts, accounts, window).
Threat modelingFolded into reconIts output (asset list + abuse cases + trust boundaries) is what recon already produces.
ExploitationDroppedRed-team deliverable, not web-app deliverable. Clients buy "find the bug, prove it exists, document the fix" — not chained pivots.
Post-exploitationDroppedSame reason. A /pentest-exploit phase would mostly be a checklist of destructive actions HITL already gates.

Genuinely missing — add on signal, not reflex

GapWhen it bitesFix
Retest / remediation verificationClient fixes findings → asks "confirm the fix landed"/pentest-retest <slug> — re-run the affected check, diff old vs new evidence. First to add when a client actually asks.
Exploit chainingTwo mediums chain to a critical (open redirect + OAuth state reuse → ATO)No new phase. Add a chains: list in engagement.yaml + a hunt note in /pentest-roundout.

Decision rule: don't add a phase because a model lists it. Add a phase when a real engagement surfaces work the existing six can't absorb.

8. Free-stack replacements for Burp Pro

Burp Community does not ship Crawl, Active Scanner, or Collaborator. We replace each with a ProjectDiscovery CLI, invoked from phase skills via Bash — not through MCP (these are not BApps).

Goal: match Pro Scanner depth, not just breadth. Pro's edge is (1) headless-Chrome DOM execution and (2) stateful session handling. The free stack closes both with a clean division of labor.

Katana crawls, Nuclei scans. Katana -headless executes JS in real Chrome to discover SPA routes — it never scans. Nuclei -headless runs client-side templates (DOM-XSS, prototype pollution, postMessage) against the URL list it is handed — it never crawls. We need both because Nuclei can only scan URLs it already has, and SPA routes only exist after a browser renders the page.
Pro featureFree alternativePhase
Crawl (headless-browser crawler + sitemap)Katana — fast pass + -headless -system-chrome deep passrecon → verify_queue
Active Scanner (fast HTTP)Nuclei + community templatesinject
Active Scanner (DOM / client-side)Nuclei -headless, headless/ templatesinject
Authenticated scanNuclei -sf (secret-file v3.2+) or -H for static tokensinject
Collaborator (OOB)interactsh — interact.sh or self-hostedinject (SSRF, blind XSS)
Backslash-Powered Scannertools/diff_fuzz.py (in-repo)inject — novel SSTI / EL / custom-parser escapes

Why diff_fuzz is in-repo

Backslash-Powered Scanner is Apache-2.0, but it hooks IScannerCheck, which is Pro-gated. The open-source extension cannot run in Community. diff_fuzz.py is our stand-in: baseline a parameter, mutate it with probe strings, diff responses, flag divergence. Closes the last Pro-Scanner-depth gap.

Two-pass scan pattern (how we reach Pro depth)

  1. Pass 1 — fast HTTP. Katana default → Nuclei default. 80% of CVE / misconfig / exposed-panel surface in minutes.
  2. Pass 2 — headless. Katana -headless to discover JS-rendered routes → feed into verify_queue → Nuclei -headless with headless/ templates on the combined set. Catches DOM-XSS, client-side prototype pollution.
  3. Pass 3 — authenticated replay. Both passes re-run with session material from /pentest-auth (bearer via -H or flow via -sf). Hits post-login attack surface.
  4. Manual deep-dive. Anything "tentative" or anything a template can't model → MCP send_http1_request / create_repeater_tab under HITL for byte-level verification.

Rules of use (same as MCP tools)

  • Scope first. Skill filters target list through safety.load_scope before invoking.
  • HITL per invocation. State pass type, templates, severity, rate, targets. Headless is high-cost — call out -c and -rl explicitly.
  • Output to scratchpad, not reports/. Skill reads, filters, then seeds verify_queue or files findings.
  • Treat output as untrusted. URLs from target, response snippets, DOM strings. Spotlight-wrap or JSON-parse.
  • interactsh canary names in the HITL announcement. Never point SSRF at a live internal target without explicit per-call approval.
  • Auth material never in argv. Write to scratch file (chmod 600), reference by path.

9. BApp handoff

BApps run inside Burp's GUI. MCP cannot invoke them. Decide per extension: reimplement in MCP, run in GUI side-by-side, or skip.

ExtensionStatusPhaseWhy
Turbo IntruderRequiredauth, access, roundoutSingle-packet HTTP/2 race. SendHttp*Request is sequential — cannot reimplement. Catches TOCTOU, coupon replay, MFA race.
Param MinerRequiredreconHidden header + parameter discovery. Catches cache-key injection, host-header routing, backend param smuggling.
AutorizeUsefulaccessPassive swarm-replay diff for horizontal access control. Complementary to /pentest-access.
Software Vulnerability Scanner / Retire.jsUsefulroundoutA06 Vulnerable Components. Passive — reads banners + JS lib versions.
JWT Editor · Hackvertor · Logger++Skip—All reimplementable with existing MCP tools or already covered by our JSONL log.

Workflow when a skill wants a GUI-only extension

  1. Skill states tool pick + reasoning: "race-shaped endpoint — suggest Turbo Intruder, single-packet, 30 reqs."
  2. HITL gate: wait for go.
  3. User right-clicks the request in Burp → sends to extension → runs → screenshots.
  4. Back in MCP: save_finding with screenshot path and a one-line result.
  5. Re-ingest any new traffic via GetProxyHttpHistoryRegex if follow-up probing is needed.
Do not invent MCP tools for these extensions. No autorize_scan, no turbo_race. They do not exist. If a skill needs an extension capability, it goes through the GUI handoff.

12. Anticipated follow-ups

Why MCP and not a Burp extension written in Java?
A Java BApp is locked to the GUI, locked to whoever is sitting at the keyboard, and can't be driven by an AI harness. MCP is harness-agnostic (Claude Code, Codex, Cline, Cursor all speak it) and leaves Burp as the stateless engine. It also means the safety spine is in Python, where I can read and audit it, not in a jar.
Why not just use Burp Pro?
Three reasons. First, portfolio build — I need to show I can reason about the safety and workflow problem, not just buy the tool that solves it. Second, the harness-driven workflow needs to work anywhere; Pro licensing is per-seat. Third, Pro doesn't solve the model-safety problem — scope enforcement, HITL, prompt-injection quarantine, auth scrubbing in logs. That layer exists whether you're on Community or Pro.
What stops the model from going out of scope?
safety.check_in_scope() runs on every tool call that takes a URL, before the call reaches upstream. It parses the hostname and tests set membership against SCOPE_HOSTS. A miss raises SafetyBlock and the call never leaves the plugin. SCOPE_HOSTS is loaded from engagement.yaml on start_engagement and read_engagement — it is not something the model can set or widen.
What happens if a response contains "ignore all previous instructions"?
spotlight_wrap() scans every response body against five regex patterns for prompt-injection markers. On a hit it wraps the body in <untrusted-tool-output source="burp" quarantine="true"> and returns it. The skills (and the CLAUDE.md system prompt) tell the model to surface the tag, stop, and not act on the content. The tag is the signal; the model doesn't decide quarantine.
Why 8 KB cap on responses?
Context budget. A pentest surfaces many responses per phase — if each one came back at 50 KB the window would be full after five calls. 8 KB is enough for the first screen of headers + body, which is what the model needs to decide the next step. The full body is still in Burp's proxy history; get_proxy_history can retrieve the untruncated item (subject to the 5000-char-per-item upstream cap on get_proxy_http_history_regex).
What's the identity header for?
When we pentest a client, our traffic looks identical to a real attack. The client's blue team (SOC + SIEM + WAF) will see our UNION SELECTs and our directory traversals and page someone. The agreed solution is a unique header on every request — e.g. X-Pentest-ID: Otoi/juice-shop/2026-11-18 — that the blue team whitelists before the window opens. Their detections filter on that header: real attackers don't send it, we always do. HackerOne and Bugcrowd have the same convention (X-HackerOne-Research, X-Bugcrowd-Ninja). Loaded from engagement.yaml, injected server-side by safety.inject_identity_into_raw(), mirrored to standalone CLI tools via -H.
Why six phases and not eleven?
Eleven is OWASP WSTG's category count — it's a checklist, not a workflow. PTES has seven, and we drop two of those (exploitation, post-exploitation) because web-app clients buy findings, not pivots. The six phases are the shape a real engagement actually takes. More phases mean more handoffs, more state, more skill files to maintain. Fewer phases mean the model does more open-ended work per skill. Six is the point where each phase has a clear prereq, a clear deliverable, and a clear HITL posture.
What's in engagement.yaml that isn't in Burp's project file?
Three things. Phase state — Burp doesn't know what a phase is. Verify queue — items surfaced by scanner or crawl that need targeted follow-up with slug, type, severity hint, status. Burp's issue tree isn't a workflow queue. Findings index — the flat list of per-finding markdown files that the report assembler consumes. Burp's reporting is on-demand HTML/XML export, not a live index.
Why is Juice Shop the dry-run target?
It's localhost (no scope risk), it's deliberately broken across every OWASP category (every phase has something to find), and it's the de facto reference target in web-app security training. Running the full six-phase sweep on Juice Shop validates that each phase fires, each skill checkpoints, each finding files, and the report assembles — before we point it at a real client.
What happens when Burp Community restarts mid-engagement?
Burp forgets its proxy history, Repeater tabs, Intruder attacks, scanner issues. The harness doesn't. engagement.yaml, the per-finding markdown, and the daily JSONL log all survive. /pentest-resume <slug> reads engagement.yaml, reloads scope + identity header, prints the roadmap box with current ticks, and suggests the next skill. Any request we need to replay against a fresh Burp session goes through checkpoint_history → replay_history with a fresh login's auth material injected.
What's the hardest thing this project is trying to prove?
That you can drive active security testing from an AI harness without giving the model authority over what gets fired. Scope, HITL, quarantine, confinement, auth-scrub, identity header — all six are structural constraints the model cannot route around, not instructions it is asked to follow. The model is a planner and a reasoner; the operator is the authority. If that layering breaks down anywhere, the whole premise fails. The six controls are the whole value proposition.
